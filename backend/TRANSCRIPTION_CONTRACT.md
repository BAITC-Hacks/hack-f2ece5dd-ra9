# Контракт живой транскрипции — Жан / Жалгас / Аслан

Сервер уже сохраняет звук встречи в WAV и публикует законченные пятисекундные фрагменты. Модель вызывается из отдельного потока: запись звука и HTTP не ждут её ответа. Задержка появления текста равна длительности фрагмента (до 5 секунд) плюс время работы модели и обновления интерфейса. Фактическая задержка измеряется после подключения модели.

## Жан: модуль распознавания и разделения голосов

`speech/recognizer.py` подключает модуль Жана `ai/transcriber.py`: добавляет смещение таймкодов относительно начала встречи и передаёт текст в backend. Зависимости устанавливает `setup.cmd`. По умолчанию используется faster-whisper `base`, CPU/int8. Модель скачивается при первом распознавании в исключённую из Git папку `models/` и повторно используется для следующих фрагментов. Параметры перед запуском сервера: `WHISPER_MODEL` и `WHISPER_DEVICE` (cpu/cuda). CUDA отдельно не проверена.

**Диаризация пока отсутствует.** API сообщает `speaker_diarization: false`, а все реплики имеют `speaker_id: speaker-unknown`. UI должен показывать «Говорящий не определён», а не выдавать эту метку за одного человека. Жану нужно добавить настоящее разделение голосов, сохраняя контракт ниже.

```python
from pathlib import Path

def create_recognizer(session_id: str):
    # Один экземпляр на всю встречу. Здесь можно хранить состояние голосов.
    return Recognizer()

class Recognizer:
    def transcribe_chunk(self, wav_path: Path, *, start_seconds: float) -> list[dict]:
        # WAV: PCM16, частота и число каналов указаны в заголовке файла.
        # Верните окончательные реплики с абсолютными таймкодами.
        return [
            {
                "speaker_id": "speaker-1",
                "start": start_seconds + 0.5,
                "end": start_seconds + 2.4,
                "text": "Текст распознанной речи"
            }
        ]

    def close(self):
        pass
```

Код в примере показывает **формат**, а не распознаёт аудио. В рабочей реализации `transcribe_chunk` должен вызывать выбранную модель. Метод вызывается строго по одному фрагменту за раз и может вернуть пустой список, если речь не обнаружена. `speaker_id` должен оставаться одним и тем же для одного голоса на протяжении всей встречи; он не является именем человека. Для неопределённого голоса можно вернуть `speaker-unknown`. Время `start`/`end` — секунды **от начала встречи**, а не от начала фрагмента. При необходимости преобразуйте stereo/48 кГц в формат модели внутри модуля.

Граница фрагмента может разрезать слово. Экземпляр `Recognizer` живёт всю встречу и может хранить контекст между вызовами, но текущий контракт публикует только окончательные реплики внутри обрабатываемого фрагмента. Проверьте потери слов на границах тестовой записи. Если модель требует буферизации или перекрытия окон, согласуйте изменение контракта с Жалгасом до объединения веток.

Если модель выбрасывает исключение или возвращает неправильный формат, запись WAV продолжается, а статус транскрипта становится `error`. Ключи API держите в переменных окружения; не коммитьте их. Текст из модели не выдумывается сервером.

## Аслан: получение реплик в UI

После успешного `POST /api/recordings/start` ответ содержит `id` встречи. Опросите раз в секунду:

```text
GET /api/sessions/{id}/transcript?after=0
```

Пример ответа:

```json
{
  "schema_version": 1,
  "session_id": "идентификатор встречи",
  "status": "waiting",
  "revision": 2,
  "processed_chunks": 2,
  "segments": [
    {
      "id": "seg-00001-000",
      "speaker_id": "speaker-2",
      "start": 5.3,
      "end": 7.1,
      "text": "Проверю отчёт завтра",
      "is_final": true
    }
  ],
  "error": null,
  "next_cursor": 1
}
```

После обработки ответа используйте `next_cursor` в следующем запросе `?after=1`. API вернёт только новые реплики. `revision` растёт после каждого обработанного WAV-фрагмента, даже если он без речи. При повторном открытии страницы начинайте с `after=0`, чтобы восстановить весь текст. Показывайте `speaker_id` как «Спикер 1», «Спикер 2»; сопоставление с именем делает человек в UI. Реплики упорядочены по времени внутри фрагмента.

Статусы: `waiting` — ждём следующий фрагмент; `processing` — работает модель; `completed` — запись и распознавание завершены; `unavailable` — модуль модели не подключён; `error` — ошибка модели; `interrupted` — сервер перезапущен до завершения. В `error` и `interrupted` уже готовый текст сохраняется. `transcript.txt` можно скачать по `GET /api/sessions/{id}/transcript.txt`, когда хотя бы один фрагмент обработан; итоговый файл окончателен при `completed`.

Проверяйте `GET /api/status`: `speech_recognition` показывает, найден ли файл модуля. Сам факт наличия файла не подтверждает его работоспособность — ошибки вызываемой модели видны в статусе транскрипта.

## Жалгас: граница интеграции

Поток читается из `sessions/{id}/session.json` по порядку `chunks[].index`. Фрагмент становится доступен только после закрытия WAV и атомарного обновления метаданных. Сервер хранит реплики в `sessions/{id}/transcript.json` и `transcript.txt`; эти файлы и записи встреч исключены из Git. Отсутствие БД для такого локального MVP допустимо.

После обработки всех фрагментов завершённой записи статус меняется на `finalizing`.
`ai.meeting.finalize_recording` запускает локальную диаризацию при заданном
`DIARIZATION_MODEL_PATH`, анализ поручений и саммари. `result.json` сохраняется перед статусом
`completed`. Ошибка диаризации не удаляет транскрипт: она отражается в `warnings` и
`diarization_status=error`. Ненастроенная диаризация имеет статус `not_configured`.

## Итоги, имена и загрузка файла

- `POST /api/recordings/upload?filename=meeting.mp3&title=Meeting`: тело — исходные байты,
  заголовок `X-Recorder-Token` из `/api/status` обязателен. До 200 МБ, ответ 202 с `id`.
  Сервер локально декодирует файл и запускает общую обработку; ошибки отображаются в транскрипте.
- `GET /api/sessions/{id}/result`: итоговый JSON; 409, если итогов ещё нет.
- `POST /api/sessions/{id}/speakers`: `{"names":{"speaker-1":"Алия"}}`, с CSRF-токеном.
  Заменяет всю карту имён; пересчитывает связь задач с людьми и саммари.
- `GET /api/sessions/{id}/protocol.docx`: актуальный протокол, включая сохранённые имена.

Итог содержит `transcript.segments`, `tasks`, `summary`, `speaker_names`, `warnings`,
`diarization_status`. `responsible_id` — связанный голос либо null; `requires_review` означает
неполные или неоднозначные данные. Автоматические выводы в любом случае проверяются оператором.
Потоковый `/transcript` и TXT сохраняют первоначальные метки. После `completed` UI заменяет
их окончательными сегментами из `/result`. Диаризация не выполняется независимо на каждом чанке.

`speaker_diarization` в `/api/status` показывает наличие настройки пути модели, а не успешность
её выполнения. Итог конкретной встречи проверяйте по `diarization_status`.
Для старой сессии без итогового JSON повторно загрузите её WAV.
