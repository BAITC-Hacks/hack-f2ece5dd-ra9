# Интеграция экрана Поручения с backend

Этот документ описывает сохранённый UI и будущие точки подключения. Он не утверждает, что backend уже реализует эти маршруты. Серверные файлы не изменены.

## Границы модулей

- app.js: renderTasks — список и фильтр поручений; editTask — редактор; renderOverview — обзор; source / return-task — связь с исходной репликой.
- js/types.d.ts: структуры Meeting, Task, Segment.
- js/domain.js: normalizeResult переводит внешний результат в структуру UI. Новую форму ответа backend следует адаптировать здесь, сохраняя семантику полей.
- js/api.js: единственная точка сетевых запросов. По умолчанию базовый путь /api того же origin. Готовые endpoints команды подключаются здесь.
- js/storage.js: текущая реализация сохранения в IndexedDB. Это локальное хранение, не серверная история.
- js/demo.js: независимые, явно обозначенные вымышленные данные. Не используются как fallback после ошибок API.
- js/export.js: экспорт текущих исправлений в DOCX/TXT/JSON.

## Поля поручения

| Поле UI | Назначение |
|---|---|
| id | Сейчас локальный ID. При подключении PATCH нужно добавить и сохранять неизменный backend ID отдельно. |
| title | Действие, редактируется человеком. |
| assignee | Имя исполнителя или null. Не выводить автоматически из говорящего. |
| deadline | Исходный срок / уточнённая дата или null. |
| reviewed | Проверка секретарём, не факт выполнения. |
| completed | Выполнение поручения, независимо от reviewed. |
| sourceId | Ссылка на реплику в транскрипте или null. |
| quote | Исходная цитата; сохраняется после правки реплики. |
| start | Таймкод в секундах или null. Не придумывать, если отсутствует. |

Входная модель адаптера понимает tasks[].responsible, tasks[].deadline и evidence {speaker,start,quote}. Диаризация и исполнители — разные сущности. Изменение имён голосов обновляет транскрипт, но не переназначает поручения.

## Существующие клиентские вызовы

| Вызов | Ожидаемое поведение |
|---|---|
| GET /api/capabilities | asr, extensions, maxBytes; без реальных возможностей распознавание отключено. |
| POST /api/jobs | multipart audio + metadata {title,date,timezone,participants}; ответ {id}. |
| GET /api/jobs/:id | queued / processing / completed / partial / failed. |
| POST /api/analyze | Необязательный анализ готовых segments/transcript, если в импортируемом JSON нет tasks. |

Для заданий этапы upload → transcription → diarization → analysis → protocol берутся из backend. progress — реальное число или null. При неизвестном прогрессе используется неопределённый индикатор. Отмены нет без поддерживающего её API.

POST /jobs передаёт Idempotency-Key. Повтор после сетевого сбоя должен использовать тот же ключ; после terminal failed интерфейс создаёт новую попытку с новым ключом. Реальную идемпотентность обеспечивает backend.

## Подключение серверного сохранения поручений позже

1. Согласовать фактический маршрут и контракт команды. Предложение, а не реализованный endpoint: PATCH /meetings/:meetingId/tasks/:taskId.
2. Сохранить серверные идентификаторы и версию записи в normalizeResult; текущие локальные ID не использовать как серверные без согласования.
3. Передавать отдельно title, assignee, deadline, reviewed, completed. Не объединять проверку и выполнение.
4. Сохранять черновик локально до подтверждённого ответа сервера. Не терять изменения при переключении вкладок или ошибке сети.
5. Показывать «Сохранено на сервере» только после успешного ответа. Обработать конфликт версий 409 без молчаливой перезаписи.
6. При серверном экспорте передавать подтверждённую актуальную версию с правками; демонстрацию продолжать маркировать.

Пока серверное сохранение не подключено, надпись «Сохранено на устройстве» намеренно остаётся точной. Кнопки редактирования, цитаты, фильтрация и экспорт работают уже сейчас.

## Приёмка после подключения

Загрузить реальную запись → получить настоящие этапы → сопоставить имена → открыть источник поручения → исправить исполнителя и срок → проверить сохранение после перезагрузки → экспортировать актуальный протокол. Отдельно проверить отсутствующие значения, пустой/частичный результат, ошибку сервера и конфликт правок. Наличие демонстрационного примера не считается доказательством работы ASR.
